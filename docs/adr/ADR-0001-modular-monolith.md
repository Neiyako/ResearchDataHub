# ADR-0001：采用模块化单体（Modular Monolith）

| 项 | 值 |
|---|---|
| 状态 | Accepted |
| 日期 | 2026-11-04 |
| 决策者 | 架构负责人（arch） |
| 影响范围 | 全局部署形态、进程模型、依赖 |

---

## Context

ResearchDataHub 要做的是**科研数据采集与同步**：用户描述"我要 ERA5 2011–2020 的 clwc/ciwc/t/q，
1000–500 hPa"这样的科学需求，系统去找源、下载、校验、落盘、生成可交付清单。

这条链上有几个天然的特征，它们决定了架构选型：

1. **典型负载是"少量任务、每个任务很长"**。一次 ERA5 压力层请求可能对应几百 GB、几十个 GRIB 文件，
   单个文件传输从几十秒到几十分钟。不是每秒几千请求的那种负载。
2. **正确性权重远高于吞吐**。气候数据出错往往是静默的：文件下了一半、单位没对上、垂直层弄错，
   程序不报错，但结论全错。所以架构必须把"可验证"放在"跑得快"前面。
3. **交互是 CLI 与批处理**。用户在自己的工作站上跑（macOS Apple Silicon / Linux），
   或者放到课题组的一台服务器上跑定时任务。不是面向公网的 SaaS。
4. **单人／小团队维护**。M0 阶段要交付的是可读、可改、可测的骨架，不是需要 SRE 值守的系统。
5. **数据源高度异质**：NCAR RDA 提供 S3/HTTPS/Globus/Zarr 四条路径；CDS 是"提交请求→排队生成→
   取结果"的异步队列，没有静态文件目录。它们的访问模型根本不同。

在这些前提下，我需要在"单体"与"分布式"之间做选择。

---

## Decision

**采用模块化单体：单个 Python 进程，模块之间通过 `core.ports` 中的 Protocol 解耦，
由 CLI 或未来的编排层在构造时做依赖注入。**

具体形态：

```
rdh（单个可执行入口）
 └─ 一个进程
     ├─ core       契约（模型/异常/状态机/Protocol）
     ├─ config     配置加载
     ├─ 执行层      planner/scheduler/sources/transfer/integrity/storage/manifest/catalog/reporting
     └─ cli        命令解析
```

- 进程内并发用 `ThreadPoolExecutor`（传输是 I/O 密集，线程足够）。
- 持久化用**单个 SQLite 文件**（`<storage.root>/manifest.sqlite3`），单写者串行写（见 ADR-0003）。
- 模块边界靠**依赖方向矩阵 + 禁止横向 import** 强制执行（见 [`docs/module-boundaries.md`](../module-boundaries.md)）。
- Protocol 让模块之间只依赖"形状"，不依赖实现类，因此未来若真要拆分，替换点已经现成。

---

## Consequences

### 正面

1. **部署极简**：`pip install` 一个包，一条 `rdh` 命令。没有容器镜像、没有编排、没有端口。
   这对"在自己的 Mac 上跑一次 ERA5 下载"这类真实场景是决定性的。
2. **调试成本低**：一个进程，一个 traceback，一个日志文件。跨进程的链路追踪、消息丢失、
   重试重复消费这一整类问题**根本不存在**。
3. **事务性强**：状态推进与事件写入在同一个 SQLite 事务里原子提交（`ports.py:347` 的要求）。
   在分布式系统里，这需要 saga 或 outbox 模式，复杂度高出一个数量级。
4. **测试便宜**：全部单元测试在 0.1–0.5 秒内跑完（实测 269 个用例），可以用 fake 替换适配器
   而不需要起任何容器。
5. **模块边界仍然硬**：虽然是一个进程，但 `core` 不依赖任何人、执行层互不 import、
   全部走 Protocol——这保证了未来拆分的可能性，同时今天不付分布式的代价。
6. **单人可维护**：代码总量可控，mypy strict 通过，新人一天能读懂。

### 负面（如实记录）

1. **单机天花板**：受限于本机磁盘、带宽、CPU。一个 10 TB 的 CMIP6 全量请求跑不动。
   - 缓解：这是**明确的产品边界**，不是缺陷。目标是"研究生在一台工作站上把一次分析要的数据
     可靠地拿到手"，不是做数据中心的批量分发。
2. **无法跨机器共享状态**：两台机器各自有一个 SQLite，不互通。
   - 缓解：如果需要共享，把 `storage.root` 放在共享卷上并保证只有一个写者；
     或者 M2 再考虑远端 Manifest。当前不做。
3. **崩溃恢复需要自己管**：没有外部调度器兜底，进程挂了要自己检测过期任务
   （`is_stale()` / `recover_stale()`，[`state.py:310-347`](../../src/researchdatahub/core/state.py#L310)）。
   - 缓解：这套机制已经在 M0 落地并测试。
4. **SQLite 写并发受限**：见 ADR-0003。代价是写入必须串行化。
   - 缓解：写入频率远低于传输频率，串行化不构成瓶颈。
5. **模块纪律靠人守**：没有进程边界时，一次错误的 `import` 不会被运行时拦住。
   - 缓解：依赖矩阵 + `grep` 检查 + 边界检查脚本（[`docs/module-boundaries.md` §4](../module-boundaries.md)）。
     M1 应把它接进 CI。

## Alternatives considered

### 微服务（planner / scheduler / transfer / manifest 各一个服务）

**为什么拒绝**：

- **不存在需要独立伸缩的组件**。微服务的核心收益是"某个组件是瓶颈时单独扩容"。
  在本系统里，瓶颈永远是"远端带宽"和"单文件的下载时长"，不是本机的某个模块。
  拆成服务后，scheduler 还是只能等 transfer 返回，没有任何东西变快。
- **把一次原子操作拆成了分布式事务**。任务状态推进 + 事件写入 + 文件登记必须在同一个事务里
  （`ports.py:347`）。在单体里这是一行 `BEGIN ... COMMIT`；在微服务里需要 saga、补偿事务、
  幂等重试，且失败路径从 1 条变成 N 条。
- **运维成本由单人承担**。四个服务意味着四份配置、四份日志、四个健康检查、一个服务发现。
  代价真实且立即发生，收益在这个规模下为零。
- **调试从"看 traceback"变成"串日志"**。

### 消息队列（Kafka / RabbitMQ / Redis 队列）

**为什么拒绝**：

- **队列解决的问题这里都不存在**。Kafka 的核心价值是"高吞吐的持久化事件流 + 多消费者解耦"。
  本系统的任务量是**每天几十到几百个任务**，不是每秒几万条消息。用 Kafka 承载这个量级是
  用航空母舰送快递。
- **引入"至少一次"语义会制造重复下载**。队列默认至少一次投递，需要业务侧做幂等。
  而这里的幂等代价很高：一个 5 GB 文件重复下载，既浪费带宽也可能覆盖正确结果。
  单体里用 SQLite 的 `expected_state` 做乐观并发控制（`ports.py:354`）就解决了，
  且失败是立刻可见的。
- **多一个必须活着的中间件**。本机跑一次下载要先把 Kafka 起来，这对目标用户是不可接受的。
- **状态双写风险**：任务状态在 SQLite、消息在 Kafka，两者不一致时以谁为准？
  单体里只有一个事实来源。

### Celery（分布式任务队列）

**为什么拒绝**：

- Celery 的价值是"把任务分发到多台 worker 机器"。本系统是**单机 I/O 密集**场景，
  `ThreadPoolExecutor` 已经能跑满带宽——瓶颈在网络，不在 CPU。
  实测一个 4 线程摄入 200 MB/s 的链路，Python GIL 完全不是问题（传输是阻塞 I/O，会释放 GIL）。
- **Celery 的 broker + result backend 是两份额外状态**，且与 SQLite 的 Manifest 形成
  "谁说了算"的冲突。
- **重试语义冲突**：Celery 有自己的 retry 机制，而本系统的重试是**状态机的一部分**
  （`RUNNING → RETRY_WAIT → QUEUED`，`state.py:115`）。两套重试叠加会产生难以排查的重复执行。
- **调试代价**：worker 是独立进程，异常要跨进程传递，`task_id` 上下文丢失。

### PostgreSQL

**为什么拒绝**：

- 目标用户是**研究生的个人工作站**。要求装 PostgreSQL 服务器（或跑容器）才能下载数据，
  这是人为的门槛。
- 本系统的写入模式是"每任务几次写入，总量万级行"，SQLite 绰绰有余。
  PostgreSQL 的全部优势（MVCC 高并发写、复杂索引、连接池、复制）在这个负载下都用不上。
- **零依赖部署**是产品要求：`pip install` 之后就能跑。
- 迁移成本低：`ManifestRepository` 是 Protocol，未来若真需要多机共享，加一个 PostgreSQL
  实现即可，上层代码不用改。这正是模块化单体的价值——**今天不做，但门是开着的**。

### 对比表

| 方案 | 本场景能否解决真实问题 | 引入的新问题 | 采用 |
|---|---|---|---|
| 模块化单体 | 能（单机 I/O 密集） | 模块纪律需检查 | ✅ |
| 微服务 | 不能（无可独立伸缩组件） | 分布式事务、运维、调试 | ❌ |
| Kafka | 不能（量级不匹配） | 中间件依赖、至少一次语义 | ❌ |
| Celery | 边际（单机多跑几个线程即可） | 双份状态、重试语义冲突 | ❌ |
| PostgreSQL | 不能（负载远未到） | 部署门槛 | ❌ |

## 何时应该重新评估

以下任一条件成立时，本 ADR 应被重新审视（**不是现在要做的**）：

1. 单次请求的规模超过单机磁盘（例如 CMIP6 全量），需要分布式存储；
2. 需要多用户共享一个任务队列与状态库（组内协作平台）；
3. SQLite 写冲突成为实测瓶颈（写入 QPS 持续高于数百）；
4. 需要长期运行的服务化 API（而不是 CLI）。

在此之前，保持单体。
