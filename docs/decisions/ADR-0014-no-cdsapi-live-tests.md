# ADR-0014：禁止用 cdsapi 做联网抓取测试

- 状态：Accepted
- 日期：2026-11-05
- 决策人：Lead（首席架构师），依据用户明确指令

## 背景

用户明确指示：**"不要用 cdsapi 做任何抓取测试，那都是浪费时间。"**

这一指令与既有的测试策略产生冲突需要裁决：仓库已有 `cdsapi` 相关的联网用例
（`tests/integration/test_sources_cds_network.py`，标注 `@pytest.mark.network`，默认不跑），
以及 `benchmarks/m6/` 里 2026-11-04 的历史实测数据（CDS 30.2 s 小请求 / ≥2700 s 拥塞期未就绪）。

CDS 的真实问题是**数据集级排队**：一次真实下载可能等待 45 分钟以上，
作为回归测试的等待成本不可接受，且结果不可重复（受平台拥塞影响）。

## 决策

1. **本轮及以后，禁止新增任何依赖 `cdsapi` 发起真实取数的测试或脚本**。
   包括：`Client().retrieve()`、`datastores` 真实请求、`benchmarks/` 新增真实 CDS 下载。
2. 保留**不发起取数**的 CDS 相关验证，它们成本低且价值高：
   - **离线**：请求翻译（`CdsRequestTranslator`）、schema 校验、`CdsApiTransport` 的协议帧构造、
     错误映射、凭据存在性检查 —— 全部可用 fixture/mock 覆盖，这部分测试继续维护；
   - **只读目录探测**（不产生数据请求、不入队、不消耗配额）：CDS catalogue/schema 的元数据 GET，
     标注 `@pytest.mark.network`，默认不跑，仅在人工确认时执行。
3. 历史实测数据（`benchmarks/m6/`）**保留原样并标注测量日期**，作为"CDS 队列特性"的事实依据，
   **不重新测量、不冒充为新数据**。
4. 涉及 CDS 的端到端场景（M7 场景 A）**改为离线端到端**：
   用真实的 `CdsApiTransport` + 真实的 `scheduler`/`integrity` 链路，但远端以**本地 HTTP 服
   务器模拟 CDS API 的三步协议**（submit → poll → results → 下载），验证"协议是否正确实现"。
   同时在文档中**如实标注**：CDS 真实取数链路的最后一次实测是 2026-11-04（见 `benchmarks/m6/`），
   本轮未重新验证。

## 后果

**正面**

- 测试套件保持"可离线、可重复、秒级到分钟级"，CI 不会因 CDS 排队而假红；
- 省掉每次 30 s–45 min 的无效等待；
- 协议正确性仍然被测试覆盖（用模拟服务端严格按真实协议返回）。

**负面 / 必须如实承认**

- **CDS 真实取数链路本轮未重新验证**。这是"未验证"，不是"已通过"，README 与验收报告必须如实标注
  `CDS live retrieval: last verified 2026-11-04 (benchmarks/m6), not re-verified this round`。
- 模拟服务端可能漏掉真实平台的边界行为（例如 CDS 的 429 限流细节）。缓解：模拟端点按从真实响应
  抄录的状态码与字段构造，并在 fixture 里注明来源。

## 被否决的方案

1. **照旧跑 `-m network` 的 CDS 下载用例**：违反用户明确指令，且等待不可控。**否决**。
2. **删除所有 CDS 相关测试**：会把已有的真实协议实现变成无覆盖代码，属于"用删除来消灭失败"。**否决**。
3. **用 `preview_only` 模式真实提交但立即取消**：仍会入队占位、可能触发平台限流，且依然要等。**否决**。
